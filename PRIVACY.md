# Privacy

HowTo has no account, telemetry, analytics, advertising identifier, or
HowTo-operated inference service. In the default configuration, inference
runs on your machine.

This document describes the behavior of the current open-source CLI. Homebrew,
GitHub, Hugging Face, a configured model provider, and commands you choose to
run have their own policies and logs.

## Default local mode

For each query, HowTo sends two messages to a locally managed
`llama-server`: a fixed platform-specific system instruction and the request
you entered. The response is processed locally. Communication uses a private
Unix-domain socket with a random per-launch bearer token; the managed runtime
is started with network features and its Web UI disabled.

If you separately opt in to the beta failed-command advisor, an active shell
adapter automatically sends the raw text of a failed interactive command and
its numeric exit status to that same managed local model. The advisor does not
capture command output, the current directory, environment variables,
directory listings, or file contents. It prints the model's suggestion for
review and never executes, copies, inserts, or stages it for Tab.

Before inference, HowTo applies a conservative eligibility filter and skips
compound shell syntax, expansions, control characters, leading whitespace, and
common secret-like markers or opaque tokens. This reduces accidental disclosure
but cannot identify every sensitive value in a command.

Normal query inference does not automatically include your environment,
current directory, directory listings, or file contents either.

HowTo does make ordinary outbound download requests in two situations:

- Homebrew downloads HowTo, its build dependencies, and `llama.cpp`.
- During `howto setup`, after confirmation, HowTo downloads the pinned model artifact
  from Hugging Face. This sends normal connection metadata such as your IP
  address and HTTP headers to the model host, but not your HowTo prompts.

The model download can also be started explicitly with
`howto model install --yes`.

## Configured providers

If `server_url` is set, HowTo does not use or start the managed local model.
It sends the platform instruction and your complete request to the configured
endpoint's `/v1/chat/completions` route. The endpoint receives the selected
`model_id` and generation settings. If `HOWTO_API_KEY` is set, it also
receives that value as a bearer token.

The failed-command advisor is unavailable whenever `server_url` is configured.
It does not send failed command text, exit status, or an advisor request to the
configured endpoint. Configuration validation rejects enabling both settings;
disable `failed_command_advisor` before setting `server_url`.

Each requested alternative is generated by a separate `n: 1` completion
request, and an invalid first response can trigger one strict retry. A remote
provider may therefore receive the same request and, when set, bearer token
multiple times, and may meter each request separately. In configured mode,
`howto doctor` also sends `GET /health` and, if that is not successful,
`GET /v1/models`; those diagnostic requests include `HOWTO_API_KEY` when it
is set but do not contain the natural-language request.

The endpoint operator and every network intermediary allowed by the transport
may retain or inspect this data. Use HTTPS for remote endpoints. Plain HTTP is
not encrypted. A configured Unix-socket endpoint stays on the same host at the
transport layer, but the process behind it may have its own network behavior.

HowTo does not control a provider's training, logging, retention, residency,
or deletion practices. Review those terms before sending sensitive requests.
Reset to local mode with:

```sh
howto config unset server_url
howto config unset model_id
```

## Data stored on the machine

| Data | macOS default | Linux default | Retention |
|---|---|---|---|
| Configuration | `~/Library/Application Support/HowTo/config.json` | `${XDG_CONFIG_HOME:-~/.config}/howto/config.json` | Until you change or remove it. |
| Setup receipt and shell adapter | `~/Library/Application Support/HowTo/` | Config and data paths under `${XDG_CONFIG_HOME:-~/.config}/howto/` and `${XDG_DATA_HOME:-~/.local/share}/howto/` | Persists until removed; the receipt records the selected shell, exact managed startup paths, and whether the beta advisor prompt has already been shown. `howto shell disable` removes that adapter and its managed blocks. |
| Managed model | `~/Library/Application Support/HowTo/models/` | `${XDG_DATA_HOME:-~/.local/share}/howto/models/` | Persists across runs and Homebrew upgrades or uninstall. |
| Runtime log | `~/Library/Logs/HowTo/llama-server.log` | `${XDG_STATE_HOME:-~/.local/state}/howto/log/llama-server.log` | Rotated at server start after 2 MiB; at most the current log and one `.1` backup are managed. |
| Runtime state, local token, and pending Tab command | `$XDG_RUNTIME_DIR/howto/`, or `$TMPDIR/howto-UID/` without it | `$XDG_RUNTIME_DIR/howto/`, or `$TMPDIR/howto-UID/` without it | Server state is replaced during its lifecycle. A pending command is session-scoped, expires after ten minutes, and is deleted when inserted. |
| Cache directory | `~/Library/Caches/HowTo/` | `${XDG_CACHE_HOME:-~/.cache}/howto/` | Reserved for local cache data. |

All of these locations can be redirected under a single absolute directory
with `HOWTO_HOME`; relative values are rejected. Any XDG directory override,
or `TMPDIR` when used as the runtime fallback, must also be absolute. HowTo
creates its data directories as owner-only and writes sensitive state with
owner-only permissions.

HowTo does not intentionally save prompt history, shell command history, or a
failed-command advisor history. Advisor input is passed directly to the managed
local model and is not written to a HowTo history file. If the managed Tab
integration is active, HowTo temporarily saves the most recent eligible
generated command in its owner-only runtime directory. It is keyed to the shell
session, overwritten by the next eligible result, unavailable for `DANGER` and
`UNKNOWN` results, and atomically removed when Tab inserts it. It becomes
unavailable after ten minutes; expired files are removed by the next shell-
integration access or when integration is disabled. In addition:

- your shell may save a request passed as command-line arguments in shell
  history;
- your shell may independently retain failed commands in its normal history,
  even though HowTo does not create another history;
- the Bash advisor reads the current command from Bash's existing interactive
  history and remains inactive when that history is disabled;
- command-line arguments can briefly be visible through local process-listing
  tools;
- `llama-server` writes an operational log and its exact contents may vary by
  the Homebrew runtime version;
- terminal emulators, session recorders, CI systems, and redirected stdout or
  stderr may retain requests, generated commands, and findings;
- the shell adapter adds a marked source block to the selected startup file(s);
  Bash uses `.bashrc` plus its active login file. HowTo creates a backup before
  changing each existing file. A safe symlink in a startup path is followed
  only after a separate interactive prompt displays its resolved target and the
  exact block. Homebrew uninstall does not remove these user-owned files or
  backups;
- `--copy` places a generated command on the system clipboard, where other
  applications and clipboard-history tools may access it; clipboard helpers
  are launched without `HOWTO_API_KEY` and the same injection-sensitive
  variables removed from executed commands; and
- `--execute` gives the generated command normal user access, so that command
  can read, write, or transmit data independently of HowTo. HowTo removes
  `HOWTO_API_KEY` and selected injection-sensitive environment variables
  before launch, but the command still inherits most other caller state.

For a sensitive request, running `howto` with no arguments and entering the text
at its prompt avoids placing the request in the original shell command line.
It does not prevent terminal or runtime logging.

## Secrets

The managed local bearer token is generated randomly, stored in the private
runtime directory, and never reused as a provider credential.

The managed `llama-server` receives an allowlisted environment rather than the
caller's complete environment. In particular, HowTo does not forward proxy,
credential, or `LLAMA_ARG_*` variables that could enable prompt logging or
override its offline/private-socket launch policy.

`HOWTO_API_KEY` is read from the process environment and is not written into
HowTo's configuration by the CLI. It is sent to configured-provider
completion and diagnostic requests, then explicitly removed from the
environment of any generated command approved with `--execute` and any
clipboard helper started by `--copy`. Environment
values may still be visible to same-user debugging tools, parent processes,
crash reporters, or CI logging. Use the narrowest scope and shortest lifetime
supported by the provider. Never include a key in a support bundle.

Natural-language requests often contain paths, hostnames, project names, or
other sensitive context. Do not put passwords, private keys, access tokens, or
recovery phrases in a request, whether inference is local or remote.
Failed shell commands can also contain literal credentials or other sensitive
arguments. Leave the advisor disabled when entering such commands; disabling it
does not change the shell's own history behavior.

## Inspecting and removing local data

Use these commands to locate and inspect state:

```sh
howto config path
howto config list
howto model status
howto server status
howto shell status
howto config get failed_command_advisor
```

Disable automatic failed-command suggestions without removing the rest of the
shell integration:

```sh
howto config set failed_command_advisor false
```

Stop the managed server before removing its files:

```sh
howto server stop
howto shell disable
```

`brew uninstall howto` removes the installed formula but intentionally does
not delete user configuration, models, or logs. Review the paths in the table
above and remove only the data you no longer want. Be especially careful when
`HOWTO_HOME` or XDG variables point somewhere non-default.

Before attaching diagnostics to an issue, redact usernames and private paths,
configured endpoint URLs, prompts, commands, and any runtime-log content that
may identify your system. `howto doctor --json` contains local paths and may
contain the configured provider URL.
